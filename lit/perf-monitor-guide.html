Performance Monitor

Measures how long each of your LitElement components actually takes to render — from the moment it connects to the DOM until its first committed update is complete. No build step, no instrumentation, no changes to your components.

New here? lit-debug-suite is a floating debug panel you drop into any LitElement app. It has 12 diagnostic tools that activate at runtime with no code changes to your components. The Performance Monitor is one of those tools.

To open the panel: set window.__LDS_DEBUG__ = true in the DevTools console, then click the 🐞 badge that appears in the bottom-right corner.

The problem it solves

Your page feels sluggish. You open Chrome DevTools. You see a 700ms scripting block in the flame graph. Which component caused it? You can't tell without drilling through dozens of nested anonymous function calls.

You add a console.time(), rebuild, reload, reproduce the issue. You get one number for one component. Repeat for every suspect. This is a ten-minute loop for a one-sentence answer.

The Performance Monitor answers the question automatically: for every custom element on the page, every time it mounts, for your entire session, without a build step.

Quick start

You do not need to install anything extra. If lit-debug-suite is already wired into your app (or you're using the Chrome extension), this is all it takes:

  1. Enable in the DevTools console 
    // Paste this before the page loads (or after — data from new mounts is collected)
window.__LDS_PERF_ENABLED__ = true;

    Or enable all tools at once: window.__LDS_DEBUG__ = true

  2. Reload the page

    The flag must be set before elements mount. After reload, every component connection is timed.

  3. Use your app normally

    Navigate, click, open modals, load routes. Each component mount is recorded automatically.

  4. Click the 🐞 badge → Perf tab

    Or print a sorted report directly in the console:

    window.__LDS_PERF_REPORT__();
✓

Setting the flag after the page loads works too. Components that mount after you set the flag are measured. Components that already mounted are not. If you need to measure a component that's already on screen, you need to reload after setting the flag.

How TTI is measured

TTI (time to interactive) is the gap between the moment a component connects to the DOM and the moment its first render has fully committed — meaning the DOM has been updated and is ready for user interaction.

For LitElement components, this is measured using el.updateComplete: a Promise that Lit resolves after the first committed DOM update, including any microtask batching that coalesced property changes before the first render.

Fig 1 — TTI measurement timeline (Lit path)

Why updateComplete — not updated()?

updated() fires after Lit patches the DOM, but it runs synchronously inside the update cycle. Data fetches, child component renders, and side effects triggered from updated() are not yet reflected in what the user sees. updateComplete resolves as a microtask after the full synchronous update cycle completes, making it the earliest moment the rendered output is stable for the user.

Fig 2 — Lit update cycle vs measurement window
  connectedCallback()
  │
  ├─ super.connectedCallback()      ← Lit queues the first update
  │
  ├─ [your init code runs]
  │
  └─┐   Lit microtask scheduler
    │
    ├── performUpdate()
    │   ├─ willUpdate(changedProps)
    │   ├─ render()                   ← template function runs
    │   ├─ DOM patching
    │   └─ updated(changedProps)    ← fires synchronously
    │
    └── updateComplete resolves        ← ← ← this is t₁
        │
        └── perf.js records: t₁ - t₀ = TTI

Fallback mode (non-Lit elements)

For elements that don't have updateComplete (plain custom elements, non-Lit frameworks), the fallback measures the synchronous duration of connectedCallback itself. This is less accurate — it does not capture async rendering — but is still useful for detecting elements that do heavy synchronous work in their connection phase. 

// perf.js — simplified
function attach(el) {
  if (!window.__LDS_PERF_ENABLED__) return;
  const tag = el.tagName.toLowerCase();
  const t0  = performance.now();

  if (el.updateComplete?.then) {
    // Lit path: measure to first committed render
    el.updateComplete.then(() => _record(tag, performance.now() - t0));
    return;
  }

  // Fallback: measure synchronous connectedCallback duration
  _record(tag, performance.now() - t0);
}
ℹ

attach(el) is called from LitDebugMixin.connectedCallback, which means elements that don't use the mixin are not measured. If you see a component missing from the Perf tab, check that it extends a class that includes LitDebugMixin.

Slow render detection

Every measurement is also checked against a threshold. Renders over 500ms generate a console warning and are added to a separate slow-render log.

Good (< 100ms)
Acceptable (100–300ms)
Slow (300–500ms)
Very slow (> 500ms — warned)

Only the >500ms zone triggers a console warning. All zones are recorded in window.__LDS_PERF__.

What a slow render console warning looks like

⚠ [LdsPerfMonitor] <rock-grid> slow render: 823ms

The threshold is hard-coded at 500ms. This is a deliberate choice — 500ms is the boundary at which a render is definitely user-perceptible as a freeze, not just a brief jank. The slow render log (window.__LDS_SLOW_RENDERS__) captures up to the last 100 slow events across all components, each with a stack trace.

⚠

The threshold is not configurable today. Components that render in 200–400ms — perceptible but below 500ms — do not trigger a warning. You can spot them in the Perf tab where they appear with an orange average render time. See What can improve for the design rationale.

The data it collects

All measurements are stored live in window.__LDS_PERF__. The object is a plain dictionary keyed by lowercase tag name. Each entry is updated in place every time that component mounts. 

// window.__LDS_PERF__
{
  "rock-grid": {
    count:    47,        // total number of times this element mounted
    totalMs:  18682,     // sum of all TTI measurements
    avgMs:    397,       // derived: totalMs / count
    maxMs:    1243,      // worst single render
    minMs:    82,        // best single render
    samples:  [212, 345, 823, 91, ...] // last 20 measurements (ring buffer)
  },
  "product-tile": {
    count:    192,
    totalMs:  8064,
    maxMs:    184,
    minMs:    28,
    samples:  [41, 38, 55, 44, ...]
  }
}
Field Type What it means When it's interesting
count number How many times this element mounted during the session High count on a leaf component may indicate redundant re-mounting
avgMs derived totalMs / count — mean TTI across all mounts This is the headline number. >100ms warrants investigation
maxMs number Worst-case single render Large max with low avg = occasional spike (data-dependent render)
minMs number Best-case render (often the warm-cache case) Very low min with high avg = cold-start penalty or race
samples number[] Last 20 individual measurements (ring buffer, newest last) Use to spot trends: is it getting worse over time?
✓

The count field is the render count, not just the slow-render count. Every mount is recorded, regardless of how fast it was. This makes it double-duty: it tells you both render speed and mount frequency. A component with count: 200 and avgMs: 25 is fast individually but may be unnecessarily mounting 200 times — that's a different kind of problem.

Expanding a row

Click any component row to see its last 20 individual render times displayed as a mini-sparkline. This helps you distinguish:

  • Consistent slowness — all 20 samples are high. The component always renders slowly regardless of state.
  • First-mount spike — first sample is high, remainder are low. Cold start or lazy data fetch on first connection.
  • Degrading trend — samples increasing over time. State growing in a way that makes re-rendering more expensive with each mount.

Design internals

Understanding how the tool is built helps you judge when to trust it and when to be skeptical.

Zero-overhead when off

The first line in attach(el) is a guard: 

if (!window.__LDS_PERF_ENABLED__) return;

When the flag is not set, the function returns immediately. No closures, no allocations, no Promise callbacks. The call from the mixin's connectedCallback is effectively free.

The ring buffer (last 20 samples)

Storing all measurements per session would use unbounded memory on long sessions or components that mount hundreds of times. The samples field is capped at 20 entries, dropping the oldest when full: 

if (d.samples.length > 20) d.samples.shift();

20 is enough to spot a trend or calculate a rolling average. The mean across all renders is still accurate (tracked via totalMs and count); only the fine-grained sample history is capped.

One Promise per mount — not per render

The measurement covers the initial mount: connectedCallback to updateComplete. Subsequent property changes and re-renders are not measured individually by this tool (that's the job of the Prop Audit tool with __LDS_PROP_DEBUG__). This is a deliberate scope decision — initial render time is the most user-visible performance metric, and measuring every re-render would add overhead on update-heavy components.

Sharing the raw object with the panel

window.__LDS_PERF__ = _data is set once at module load and the panel reads it directly. There is no serialization, copy, or message-passing. This means the panel always shows live data without any refresh mechanism — it reads the object the same way the console does.

Reliability

The Performance Monitor is one of the more reliable tools in the suite. Here's an honest breakdown of what you can and can't trust.

What is highly reliable

  • The count. count is a simple integer incremented each time a component mounts. It is accurate as long as attach(el) is called from connectedCallback.
  • The maxMs. The worst-case measurement is real — a slow render that happened in this session. It may not be reproducible on demand, but it happened.
  • Relative ranking. If rock-grid is consistently 10× slower than product-tile in the sorted table, that relationship is reliable even if the absolute numbers have variance.

What has meaningful variance

  • avgMs on low-count components. A component that mounted once has count: 1 and avgMs: X — that's a single data point. It may have been a cold-start load. Don't over-index on it.
  • Absolute milliseconds across machines. A 200ms TTI on a developer MacBook Pro may be 1200ms on a low-end Android. The numbers reflect the machine running the session, not production conditions.
  • First-run vs warm measurements. Browser JIT compilation, module caching, and network conditions affect the first few renders. Mount the component a few times before drawing conclusions about its typical performance.

What is not reliable

  • Mounts that happen before the flag is set. If the page already mounted before you set __LDS_PERF_ENABLED__, those renders are not recorded. Always reload after setting the flag for a clean session.
  • Async work triggered from updated(). If a component fetches data in updated(), that fetch is not included in the measured TTI — the measurement completes at updateComplete, which resolves before the fetch returns. The component appears fast in the Perf tab but may still feel slow to the user because it re-renders when data arrives.

Limitations

Initial mount only

TTI is measured for the first render of each element instance. Subsequent re-renders triggered by property changes are not individually timed. To measure re-render performance, use __LDS_PROP_DEBUG__ (the Prop Audit tool), which tracks render reasons and thrash.

No per-instance tracking

Measurements are bucketed by tag name, not by instance. If you have 50 instances of <product-tile>, they all contribute to the same product-tile entry. You cannot tell which specific instance was slow. For instance-level debugging, use the Inspector tool (__LDS_INSPECTOR__).

Components not using the mixin are invisible

attach(el) is called from LitDebugMixin.connectedCallback. Any custom element that does not extend a class using the mixin will not appear in the Perf tab — even if it's a LitElement. This includes third-party elements and elements you haven't migrated to the mixin yet.

Does not account for async rendering patterns

// This render pattern is measured short:
connectedCallback() {
  super.connectedCallback();
  // updateComplete resolves here — TTI = fast
}

updated() {
  this.fetchData().then(data => {
    this.data = data;  // triggers a SECOND render — not measured
  });
}

The measured TTI is for the first (skeleton) render, not the data-loaded render the user actually waits for. The user experience is slower than the numbers suggest.

DevTools throttling affects readings

If you have CPU throttling enabled in DevTools (4× or 6× slowdown), your TTI numbers will be proportionally inflated. This is expected behavior — it reflects performance on slower hardware — but be aware when comparing against baselines taken without throttling.

!

Do not use Perf tab numbers directly in performance budgets or CI gates. The measurements are relative and machine-dependent. For absolute production performance budgets, use Real User Monitoring (RUM) tools. The Perf Monitor is an investigation tool, not a reporting tool.

What can improve

These are honest gaps in the current implementation. None are blocking, but each represents a real use case the tool doesn't serve well today.

1. Configurable slow-render threshold

The 500ms threshold is hard-coded. In a complex dashboard app, 200ms renders may be the norm and worth flagging. In a simple static page, 800ms may be acceptable. An improvement would be window.__LDS_SLOW_RENDER_THRESHOLD_MS__ = 200 to let teams set their own bar.

2. Re-render measurement

The tool measures initial mount TTI but not the time for subsequent re-renders (property changes, parent rerenders). Many performance issues are in the ongoing render performance of components that update frequently (data grids, live feeds). A separate __LDS_RERENDER_PERF__ metric that hooks into willUpdate/updated would fill this gap.

3. Render count history over visibility cycles

The count field accumulates forever for a session, but there's no breakpoint at page navigation or visibility change. A component that mounts 200 times across 10 navigation cycles is fine (20/cycle). A component that mounts 200 times in one cycle is suspicious. Pairing with the cycle tracking from window.__LDS_MOUNT_CYCLES__ would make this distinction automatic.

4. P95/P99 instead of max

maxMs is sensitive to outliers — one anomalous render during page load can make a fast component look terrible. P95 and P99 latency percentiles would give a more stable signal for components with high mount counts.

5. Async render tracking

As noted in the limitations, components that render a skeleton and then update with data appear fast in the Perf tab. A reportTTI() manual method that developers could call when their component is truly ready (after data loads) would give a more accurate user-facing measurement.
