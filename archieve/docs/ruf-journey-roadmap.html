How one small curiosity — wanting to inspect a running RUF element without opening DevTools — became a full observability suite embedded into the base mixin of 86 web components.

The Spark

It started with a single question

The original idea

The question was simple: "Can we see the live property values of a RUF component without opening Chrome DevTools and digging through the shadow DOM?" Every time a customer reported a weird state — a grid not refreshing, a dropdown showing stale options — support had to either reproduce it locally or schedule a screen share.

The answer was a hover badge. A small overlay that would appear on any RUF component when you moused over it, showing its current properties. That was ruf-inspector.js. And that was the end of "just one small thing."

The first realization

Building the inspector revealed something important: to show property values, you need to hook into the element's lifecycle. And if you're already hooked into the lifecycle, you can measure how long renders take. And if you're measuring renders, you can log the slow ones. And if you're logging slow ones, you need a place to put them — a structured store, not a console log.

The pattern emerged before the tools did: intercept at the base layer, store structured data, surface it on demand. Everything that came after is an expression of that pattern.

Key insight: The value isn't in any single tool. It's in the architecture that makes every tool free — because the interception point is shared, and the activation is global.
Evolution

Seven rounds of building on one idea

Each round answered a question that the previous round made possible to ask. The inspector revealed the need for perf. Perf revealed the need for cause. Cause revealed the need for AI routing. The suite grew by following the questions.

Origin

The Hover Inspector

ruf-inspector.js

A mouse-over badge that overlays the live property state of any RUF element. Simple, immediately useful, and the technical foundation for everything else — because it proved you could hook into the element lifecycle without changing any of the 86 components.

"If we can read properties, we can measure them. If we can measure them, we can flag bad ones."
1
Phase 1

Foundation — Zero-Overhead Base

7 tools Master gate

The inspector became one of seven tools. Error boundary, perf tracker, ACI tracer, memory monitor, slow API logger, and prop audit were added alongside it — all wired into ruf-element.js with a single master flag.

The critical architectural decision: static imports that instrument nothing by default. The tools exist in the bundle; the instrumentation does not run until activated. This made it safe to ship to production.

ruf-error-boundary — crash catcher with fallback UI
ruf-perf — TTI per component tag
ruf-memory — mount/unmount counters via FinalizationRegistry
ruf-aci-tracer — ACI dispatch timeline

Phase 2

The Panel — Support Without DevTools

ruf-debug-panel.js 8 tabs

Tools are only useful if someone can read their output. A floating debug panel — the 🐞 badge — gave support teams and customers a way to see all data without needing DevTools. The panel's most important feature: the JSON download button.

For the first time, a customer could click one button and email support everything — errors, perf, memory, ACI events — as a structured file. No screen share. No reproduction session. Just a file.

ruf-console — console.error/warn ring buffer
ruf-debug-panel — floating badge, 8-tab panel, JSON download
2.5
Phase 2.5

Import, History & Pinpoint — Making Data Actionable

Pinpoint tab Import mode Fix Table

A downloaded JSON report is only useful if someone reads it and understands it. The Pinpoint tab changed this: instead of making engineers parse raw data, it aggregates all issues across all tools into a single prioritized list — each with a file path, severity, and a plain-English recommendation.

The History tab ensured nothing was lost across refreshes. The Import mode let support engineers load a customer's report and browse it exactly as the customer saw it. The Fix Table made every issue a structured work item.

🔍 Pinpoint tab — aggregated issues with file paths and recommendations
📋 History tab — 20 snapshots, persisted across refreshes
📥 Import mode — load customer reports without being on their machine
Fix Table export — structured JSON for engineering triage
R1
Round 1

Complete Observability — Vitals, Network, HTML Report

ruf-vitals ruf-network Health score

Page-level health required Core Web Vitals and network visibility. ruf-vitals.js wired into the PerformanceObserver API. ruf-network.js patched fetch and XHR globally. Together they provided the full picture: not just "which component is slow" but "what is the actual user experience".

The HTML report made the output shareable to anyone — no viewer needed, no JSON parser. A self-contained page with all 12 tool outputs, openable in any browser.

ruf-vitals — LCP, CLS, INP, Long Tasks with good/needs/poor classification
ruf-network — all fetch/XHR with status, duration, size, error flags
Page health score — 0–100 grade derived from all tool data
HTML export — self-contained report, no viewer required
R2
Round 2

The Causality Layer — Why, Not Just What

Render reasons Thrash detection Cycle detector Falcor decode

Knowing a component re-rendered 47 times is useful. Knowing it re-rendered because a parent passed a new [] literal on every render cycle — while a sibling was dispatching the same ACI action 80 times per interaction — is actionable. Round 2 moved from observation to causality.

The Falcor decoder was the most technically complex piece: form-encoded POST bodies and JSON-embedded GET params, decoded in real-time, surfacing entity types and operations that were completely invisible in standard DevTools network tabs.

R2-A: Render reason tracker — per-property old/new value summaries in Perf tab
R2-B: Property thrash detector — flags >5 sets/sec, highlights in Pinpoint
R2-C: ACI frequency table — dispatch counts, source elements, hot-action flags
R2-D: Cycle detector — DFS on directed update graph, chain path in Pinpoint
Network: Falcor POST decoder — domain, operation, entity types, pagination, filters
R3
Round 3

DOM Health, Auto-POST Crashes & History Diff

DOM stats Auto-POST History diff Falcor GET

DOM bloat is one of the most common performance issues in Polymer-heavy SPAs — thousands of custom element instances living in the DOM simultaneously. R3 added snapshot-time DOM counting, letting the panel surface "you have 4,200 DOM nodes, 840 of which are pebble-grid-cell".

The history diff answered the hardest support question: "it worked on Monday." Select two snapshots, hit Compare. The diff view shows exactly which metrics degraded, which issues appeared, and which components are new.

DOM stats — node count + custom element breakdown at snapshot time
Auto-POST crash — report POSTed to configurable endpoint before customer calls support
History diff — select two snapshots, compare metrics, issues, and component sets
Falcor GET decoder — embedded JSON-string params from /data/*.json?paths= URLs
R4
Round 4

The Claude Pipeline — Closing the Loop

claudePrompt lineNumber readHint relatedComponents

The Fix Table export has always been a JSON. Round 4 made it a direct AI input. Each issue now includes the exact line number from its call stack, a readHint instruction telling Claude which file and line range to read, a list of ACI-related components that share the same action names, and a ready-to-paste claudePrompt.

The loop is now: customer encounters issue → report downloaded → Fix Table uploaded to Claude → Claude reads file at line → Claude applies fix → PR created. No exploration, no clarifying questions, no back-and-forth. One structured input, one targeted change.

lineNumber — parsed from filtered call stack's first app-source frame
readHint — "Read src/elements/tag/tag.js lines N-10 to N+10"
relatedComponents — components sharing ACI actions with the affected component
claudePrompt — severity + issueType + file:line + recommendation in one sentence
The Pattern

Each round followed the same logic

The suite grew by answering the question that the previous answer made it possible to ask. This isn't accidental — it's the natural shape of observability work. Each layer of insight exposes the next unknown.

Inspector →

Seeing live properties raised the question: which properties are causing performance problems?

Perf →

Seeing slow components raised the question: why are they re-rendering so often?

Causality →

Seeing render reasons raised the question: are the API calls also the problem?

Network →

Seeing decoded Falcor calls raised the question: who reads these reports and acts on them?

Fix Table →

Seeing structured issues raised the question: can AI apply the fix directly?

Claude pipeline →

Having a working loop raises the question: can this work for any framework?

What's Next

The roadmap follows the same pattern

Each phase generalizes what the previous phase proved — from Syndigo-specific to framework-specific to universal. The end state is a developer tool available to every frontend team, from the same place a developer already works.

Round 5 — Accessibility & Duplicate Detection

Next

The last uncharted observability dimension: accessibility and load efficiency. Two tools, both low complexity, high value for the same support workflow.

♿
A11y checker — axe-core on-demand scan via dynamic import. Results surface in Pinpoint with WCAG criterion, element selector, and fix recommendation.
🔁
Duplicate import detector — Scans performance.getEntriesByType('script') for the same module loaded from both src/ and lib/. Flags the version mismatch that causes silent class identity failures.
🎬
Session replay sketch — Reconstruct the user's session narrative from ACI timeline + mount sequence. No screen recording. Just the story of what the app did.
G1

Generic Lit — lit-debug-suite package

Near-term

Extract everything that is framework-specific (LitElement lifecycle hooks, requestUpdate, performUpdate) from everything that is architecture-specific (master gate, structured globals, panel). Publish as a standalone npm package.

📦
lit-debug-suite — Drop-in mixin for any LitElement base class. Same activation model, same report format, same panel. Zero RUF-specific code.
🔌
Adapter interface — A thin FrameworkAdapter interface — onMount, onRender, onPropChange — that each framework implementation satisfies. The tools consume the adapter, not the framework directly.
📄
Shared report schema — Versioned JSON schema for the report format. Tools from different frameworks produce reports that the same panel can read.
G2

React Adapter — react-debug-suite

Medium-term

Implement the FrameworkAdapter for React. The React Profiler API, DevTools hooks, and custom hook wrappers give direct access to the same lifecycle signals. The output format is identical.

⚛️
useRufDebug provider — A React Context provider wrapping the app root. Instruments render cycles via React Profiler. No per-component code needed.
🔗
Fiber adapter — Maps React fiber update causes (state, props, context, hooks) to the same property-change events the panel understands.
📊
Same panel, same report — The ruf-debug-panel ships as a standalone web component (not a React component). It reads window.__RUF_* globals regardless of how they were populated.
IDE

VSCode Extension — Debug reports in the editor

Medium-term

The fix table already knows the file and the line. A VSCode extension closes the gap between reading a report and opening the code — the extension does both, in the editor.

📂
Report watcher — Extension watches a configured path for new ruf-fix-table-*.json files. When one appears, a notification surfaces in VSCode.
🎯
Jump-to-issue — Clicking any Pinpoint issue in the extension panel opens the file at the exact line, with the issue and recommendation shown in a hover or Problems panel entry.
🤖
Claude Code integration — One-click "Fix with Claude" — the extension opens a Claude Code session with the claudePrompt pre-filled and the file already open. The developer reviews and approves the PR.
📈
Cross-session trends — The extension indexes all imported reports, surfacing recurring issues across sessions and customers — a signal that a component needs systematic attention, not a one-off fix.
∞

Universal Deployment — Any framework, any team

Vision

At full scale, the debug suite is not a product — it's a pattern that any frontend team can adopt. The activation model, the structured globals, the Pinpoint classification, and the AI pipeline are composable primitives.

🌐
Vue / Svelte / Angular adapters — Each framework has its own component lifecycle API. The FrameworkAdapter interface maps each to the same tool layer. One panel, many frameworks.
☁️
Cloud report ingestion — Auto-POST on crash sends to a SaaS endpoint. Teams get a dashboard of production sessions, searchable by customer, by issue type, by component.
🔄
CI regression gate — Run the debug suite in CI against a Playwright session. If the health score drops, the build fails. Performance and correctness become the same check.
🤝
Shared issue registry — Issues from multiple teams' reports are classified against a shared taxonomy. A fix discovered by one team becomes a recommendation for another.
Futuristic Ideas

What becomes possible when the pattern matures

These aren't roadmap items — they're the shape of what the pattern enables once the tooling layer is stable. Each one follows from a question the existing suite makes it possible to ask.

AI → Runtime loop

Live AI diagnosis

RUF captures a session snapshot every 30 seconds. A background agent queries Claude with the delta: "performance dropped from A to C in the last snapshot — here's what changed." Claude responds with a hypothesis. No human in the loop until a fix is needed.

Predictive

Pre-crash prediction

Thrash + cycle + memory storm patterns precede crashes. An ML model trained on historical report data predicts crashes before they happen — surfacing "this session is 80% likely to crash if the user opens the attribute panel."

Structural

Architecture advisor

The ACI frequency table + cycle detector + component relationship data forms a dependency graph. An AI layer reads the graph and identifies structural anti-patterns: god components, bidirectional data flows, shared mutable state.

Onboarding

New-developer guidance

The inspector + prop audit + Pinpoint tab together provide a real-time guided tour of any running component. A new engineer enables the suite, mouses over any component, and gets an explanation of what it is, what it's doing, and why it's doing it.

Testing

Assertion from real sessions

Record a healthy session as a "golden state." Future test runs compare the live report against the golden state. Performance regressions, new cycles, and component changes become automatic test failures.

Scale

Cross-customer aggregate

Auto-POST sends anonymized reports to a central service. Teams see which issues are universal across customers (systemic, fix immediately) vs. isolated (customer-specific configuration). Priority becomes data-driven.

The north star: a developer never guesses

From the moment a customer reports an issue to the moment a PR is merged, every step should be data-driven. RUF is the layer that captures the data. AI is the layer that acts on it. VSCode is the place it surfaces. The developer approves. That's the whole flow — and it started with a small question about seeing live properties.
