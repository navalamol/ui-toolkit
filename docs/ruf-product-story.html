The Problem

Production issues die in the dark

Customers report performance problems, mysterious crashes, and blank screens — but support can't reproduce them. DevTools aren't available. Logs don't exist. The cost of each support loop is enormous.

🔕

Silent failures

Component crashes render blank without context. No error propagation, no stack trace surfaced to the user.

📉

Invisible slowness

Pages feel slow but there's no TTI data, no render timeline, no way to know which component is the culprit.

🔄

Unexplained re-renders

Components re-render dozens of times per interaction. Nobody knows why because property change history doesn't exist.

📡

Opaque API calls

Falcor requests are form-encoded. Network tabs show blobs, not what entity type or operation was actually requested.

🔁

Circular update storms

Component A triggers B which triggers A. The page thrashes. Nobody can trace the cycle without a graph.

💸

High support cost

Each issue requires a live session, screen share, and often a special build. Slow, expensive, unscalable.

What We Built

12 tools. One mixin. Zero effort per element.

Every tool is embedded in RufElement — the base mixin all 86 components extend. No per-element work. No separate imports. Globally activated, globally deactivated.

🛡️

ruf-error-boundary

Wraps performUpdate in try/catch. Logs crashes with stack traces. Renders graceful fallback. Auto-POSTs to support endpoint on critical failure.

⚡

ruf-perf

Per-component TTI tracking. Slow render log (>500ms) with call stacks. Grade A–F health per component.

🔍

ruf-prop-audit

Traces every property change. Detects property thrash (>5×/sec). Records render reasons with old→new value summaries.

🔮

ruf-cycle-detector

Builds a directed update graph. Runs DFS on every render cycle. Surfaces circular chains like A → B → A.

📊

ruf-vitals

LCP, CLS, INP via PerformanceObserver. Long Task detection. Good/needs/poor colour coding mapped to Web Vitals thresholds.

🌐

ruf-network

Patches fetch + XHR. Decodes Falcor POST and GET bodies — exposes entity type, domain, operation, pagination, sort, filters.

📡

ruf-aci-tracer

Records every ACI dispatch with timestamp and source element. Frequency table flags actions >20 dispatches.

🐌

ruf-slow-api

Patches DataObjectManager. Logs calls exceeding threshold with operation name, duration, and initiating component.

💾

ruf-memory

Mount/unmount counters via FinalizationRegistry. Detects mount storms (>20 mounts/sec). Flags potential memory leaks.

🖥️

ruf-console

Patches console.error/warn into a 200-entry ring buffer. Timestamped. Searchable. Available in report even after page refresh.

🎯

ruf-inspector

Hover badge overlays live component state snapshot — properties, element tag, component health grade, rendered dimensions.

🌳

DOM health (panel)

Snapshot-time DOM node count with custom element breakdown. Flags when >1,500 nodes. Health score deductions applied.

Architecture

Zero overhead is not a promise — it's a constraint

Every tool is statically imported once at module parse time, but instruments nothing until its flag is set. The per-element cost when debug is off: approximately 40 property reads in connectedCallback — unmeasurable at ~100–300ns.

// Three ways to activate — none require a deploy

// 1. Browser console (developer / support with DevTools)
window.__RUF_DEBUG__ = true

// 2. Selective — enable only what you need
window.__RUF_DEBUG__ = { perf: true, network: true, aciTracer: true }

// 3. Tenant flag — support sets it in globalSettings, no console needed
mainApp.globalSettings.rufDebugEnabled = true
mainApp.globalSettings.rufCrashEndpoint = 'https://support.syndigo.com/ruf-ingest'

Why static imports, not dynamic ones

Static imports parse once and are cached by the browser module graph. Dynamic imports on activation would introduce a network round-trip at exactly the wrong moment — when a customer is already hitting a problem. The parse cost of 12 small modules is paid once at startup; the instrumentation cost is zero until needed.

Why embedded in the mixin, not a separate package

All 86 elements extend RufElement. Embedding there gives universal coverage with no per-element changes, no new imports, and no coordination cost. A separate debug package would require opt-in per element — that's 86 opportunities for coverage gaps.

Support Workflow

No live session. No special build. Just a report.

The entire support workflow is designed for asynchronous operation. Support enables the flag; the customer browses; the panel captures everything; the customer downloads a file. That's the whole loop.

1

Customer reports issue

Support receives a vague complaint — "the page is slow", "it crashed", "the grid won't load".

2

Support enables the flag

One config change: rufDebugEnabled = true in the tenant's globalSettings. No code change. No deploy. Takes 30 seconds.

3

Customer browses normally

The 🐞 badge appears in the corner. All 12 tools are now capturing data silently. Customer does exactly what caused the problem.

4

Customer downloads the report

One click. The panel generates a structured JSON + self-contained HTML report. The customer emails or uploads it. Support has everything.

5

Support (or AI) reads the Pinpoint tab

The Pinpoint tab aggregates crashes, storms, slow renders, thrash, cycles, and network errors — each with a file path, line number, and a plain-English recommendation.

6

Engineer fixes the root cause

No guessing. The issue has a file, a line, a recommendation, and a list of related components. The fix is a targeted PR, not a fishing expedition.

AI Integration

Where AI can't go — and how we fill that gap

AI models don't run in the browser. They can't see what's happening at runtime. They can read code, but code doesn't tell you which component is slow, which API call is timing out, or which property is thrashing — in this customer's session, right now. RUF is the eyes AI doesn't have.

🤖 What AI does well

  • Reads source code and understands architecture
  • Suggests fixes from patterns and best practices
  • Generates tests and documentation
  • Reviews PRs for correctness and style
  • Answers questions about the codebase
AI is excellent at static analysis — but it sees a snapshot of code, not a running system.

🔍 What RUF captures that AI can't

  • Which component rendered 47 times in one interaction
  • Which Falcor call fetched 12,000 entity records
  • The exact property that triggered a re-render chain
  • That pebble-grid → pebble-toolbar → pebble-grid is a cycle
  • LCP was 8.2 seconds because of one synchronous DOM operation
RUF captures runtime truth. AI can't invent this data — it needs to receive it.

"The Fix Table export is a direct Claude input. Every issue entry includes a file path, a line number extracted from the call stack, a ready-to-paste prompt, and a list of related components — enough for Claude to open the right file, understand the context, and apply a targeted fix without a single clarifying question."

Avoiding recurring AI cost

RUF does all the heavy lifting in the browser — classification, scoring, stack parsing, Falcor decoding, cycle detection, health grading. By the time data reaches AI, it's already structured. The claudePrompt field in every fix table entry is a single sentence. AI reads the file at the right line and makes one targeted change. No exploration loop, no multi-turn disambiguation. One structured input → one correct fix.

Standalone Value

Even without AI, it solves real problems

The suite was designed to be fully useful to a support engineer or developer with no AI access. The Pinpoint tab makes every insight human-readable. The HTML report opens in any browser. The history diff answers "it worked yesterday".

Health Score

A–F grade for the full page, derived from vitals, crashes, storms, network errors, and property thrash. One number that tells you if this session is healthy.

Pinpoint Tab

Aggregates all issues from all tools. Each issue has a file path, severity, fix recommendation, and a filtered call stack showing only app code.

History Diff

Select any two snapshots from up to 20 saved sessions. The diff view shows which metrics improved, which degraded, and which components appeared or disappeared.

Falcor Decode

Every Falcor request (POST or GET) is decoded to human-readable entity type, domain, operation, pagination, sort config, and filters. No more reading raw paths.

Crash Auto-POST

On a critical crash, the report is automatically sent to a configurable endpoint. Support receives the report before the customer has even picked up the phone.

Import Mode

Support can import a customer-sent report and browse it in the full panel — all 12 tabs, all data — without being on the customer's machine.

Cost Model

Eliminating the most expensive parts of support

The traditional support-to-fix cycle requires skilled engineers, live sessions, and special builds. RUF restructures this into an async, data-driven workflow that scales with team size without proportional cost.

Before RUF

  • Special debug builds pushed to customer environment
  • Senior engineer time spent on reproduction
  • Issues closed as "can't reproduce" — customer frustrated

With RUF

  • Pinpoint tab does the triage — support reads a summary

  • History diff answers before/after comparisons instantly
  • Falcor decoded automatically — entity types visible in the panel
Scalability

The same idea, everywhere a component tree exists

The pattern — zero-overhead base mixin instrumentation, tenant-activatable, with a downloadable structured report — is framework-agnostic. The implementation is specific to Lit/Polymer; the architecture isn't.

Phase 1 — Now

Lit 3 + Polymer 3

RUF is live in ui-platform-elements. 86 components covered automatically. Activated via rufDebugEnabled.

Phase 2 — Generic Lit

Any LitElement codebase

Extract the framework-specific hooks into a standalone package: lit-debug-suite. Any team using Lit can drop it into their base element in one import.

Phase 3 — React

React + custom hooks

The same concepts map to React DevTools hooks, Profiler API, and custom hook wrappers. A useRufDebug provider wraps the app root. Same report format.

Phase 4 — VSCode Extension

IDE integration

A VSCode extension reads a locally saved report, highlights files at the issue line numbers, opens the component source, and suggests the fix — directly in the editor.

"A developer never has to open the browser to understand a production issue. They open the report in VSCode, and the extension walks them from the symptom to the exact line — the same way a debugger walks from a breakpoint to a stack frame, but for real production sessions."

Universal Principle

The model, not the implementation

What makes RUF valuable isn't its 12 tools — it's the pattern: intercept at the base layer, collect without overhead, surface structured data that humans and AI can both act on.

🏗️

Intercept at the base layer

Every framework has a base class or mixin point. That's where to instrument — not in individual components, not in a separate service, not in infrastructure.

🔇

Default-silent, activatable

Production code carries the instrumentation but never runs it. A flag — from a config, a URL param, or a session setting — switches it on. No code change. No deploy.

📦

Structured, not logged

Every tool writes to a typed global (window.__RUF_*). The panel reads from these globals. AI reads from the export. Nothing is just a console.log.

🎯

Actionable, not informational

Every issue in the Pinpoint tab has a recommendation, a file path, and a line number. The output is a work item, not a data dump.
